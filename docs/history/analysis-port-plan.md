# Analysis-tier port — execution plan for the remaining gaps

Generated 2026-06-22 from a 13-agent planning workflow (each agent deep-read its assigned Ghidra analyzer + the kuna seam). Companion to [`analysis-port-log.md`](analysis-port-log.md) (what's done) and [`missing-analyses.md`](missing-analyses.md) (the gap inventory). This is the **how-to-finish** doc: the remaining ~14 gaps organized into dependency-ordered waves for parallel worktree sub-agents.

## Execution waves

### Wave 0 — Foundation: fixtures + AnalysisOutput extensions (prereq for everything)

**Tasks:** `FIX-vendor-fixtures`, `FND-analysisoutput-fields`

Several passes need new fixtures (DWARF-stripped, switch-table, ARM-Thumb, Rust, mcount, fmt, cpp-noreturn) and three passes add new AnalysisOutput fact kinds (context_paints for arch-markers, call_fixups for callfixup, locals for dwarf-2b). Vendoring fixtures and landing the additive struct fields FIRST avoids N agents racing on the same shared files (pass.rs, fixtures/README.md, Cargo.lock for gimli). These are tiny, low-risk, human-or-solo-agent tasks that unblock the whole fan-out. Do them before any pass agent branches so worktrees start from a tree that already has their fixtures + fact fields. NOTE: the gimli workspace-dep + Cargo.lock entry also lands here (or in s1-dwarf-1's worktree first-build, committed) to avoid an offline-gate failure.

### Wave 1 — Pure additive passes — zero engine risk, independent, max parallelism

**Tasks:** `s1-eh-frame`, `s1-entry-disc`, `sourcelang`, `ruststring`, `addrtable`, `aggressive-disasm`, `operand-refs`, `s1-dwarf-1`, `s1-dwarf-2`

Every task here is a pure AnalysisPass (or a doc-only decision) bound to the real-ELF path: it only fills existing AnalysisOutput fields (entries / prototypes / symbols / readonly / strings) committed by the already-wired commit_analysis_output arms, so it CANNOT perturb the 675/158 XML datatest oracles — gate risk is structurally LOW. They are mutually independent (no shared mutable file beyond passes.rs registration + the fixtures/fact-fields already landed in wave 0). s1-dwarf-2 (signature typing) reuses the exact prototypes path s1-protos proved and depends only on s1-dwarf-1's module skeleton, so sequence dwarf-1 -> dwarf-2 within one agent's worktree chain (or two agents, dwarf-2 rebasing dwarf-1). aggressive-disasm and operand-refs are doc-only/decision tasks — cheap, assign to a single agent who can also pick up sourcelang. addrtable lands DISABLED-by-default (Ghidra parity + false-positive risk), so it is inert. This wave is the bulk of the value at the lowest risk.

### Wave 2 — Engine/console-touching passes — new commit arms, gated, must hold all 3 gates

**Tasks:** `arch-markers`, `callfixup`, `s1-formatstring-A`

These need a new commit arm or a small engine accessor beyond the existing 5 commit arms. arch-markers adds a context-paint commit arm (touches the ContextDatabase via set_variable, real-ELF-ARM-path only — but the commit-arm edit to engine.rs is shared surface, so serialize it after wave-1 entry passes that also touch engine.rs are merged). callfixup adds commit step 6 + a 3-line PcodeInjectLibrary read accessor. s1-formatstring-A is the PURE PARSER MODULE only (kuna-analysis-only, zero engine touch) — it is safe to run in parallel here and is the prerequisite for the engine-touching formatstring-B in wave 3. Run these as separate worktrees but INTEGRATE THEM SEQUENTIALLY (each re-gates all three) because they all edit engine.rs's commit_analysis_output and/or pass.rs.

### Wave 3 — Highest-risk engine seams — solo, sequential, some human-gated

**Tasks:** `engine-followups-1-printer`, `engine-followups-2-optiongating`, `engine-followups-3-noreturn-demangle`, `s1-formatstring-B`, `s1-dwarf-3`

These touch the SHARED engine surfaces that DO feed the parity gates or are structurally invasive. engine-followups-1 (printer string-literal arm in s9_emit/printc.rs) is the ONLY task in the whole plan that genuinely risks the 675-datatest + 158-stage byte-parity oracles — it MUST be solo, instrumented (A/B run to pin the exact render arm before editing), and human-reviewed. engine-followups-2 (per-run pass option-gating) restructures bootstrap commit timing + stages.toml settable counts + the catalog drift-check — invasive, touches shared console/CLI/codegen, solo. engine-followups-3 (noreturn x demangle) changes the AnalysisOutput.noreturn fact shape (address-based), rippling to pass.rs/noreturn.rs/commit — do it AFTER wave-2 pass agents stop editing pass.rs. s1-formatstring-B (decompile-loop override wiring) and s1-dwarf-3 (ScopeLocal stack-var map, engine change) are both invasive engine-driver changes gated OFF/deferred by default; they need formatstring-A / dwarf-1+2 merged first. Each integrates SEQUENTIALLY with a full 3-gate re-run; printer change goes LAST so any datatest re-baseline is isolated and obvious.

## Cross-cutting prerequisites (land BEFORE any pass agent branches)

## Fan-out / integration protocol

## Fan-out / integration protocol

### The branch-from-MAIN gotcha (read first)
Worktree sub-agents branch from **main**, not from the in-progress analysis-port branch. So each agent's worktree will NOT contain the wave-0 foundation (new fixtures, new AnalysisOutput fields, gimli dep) or any earlier-wave merge unless it explicitly pulls them in. Two options, pick per-agent:
1. **Merge-in (preferred for wave 1+):** the agent's first action in its worktree is `git merge <integration-branch>` to pull the current integration state (foundation + already-merged passes). This gives it the new fact fields/fixtures and avoids spurious conflicts.
2. **Integrator cherry-picks:** the agent works against pristine main and the integrator cherry-picks its commit onto the integration branch, resolving the additive `passes.rs`/`pass.rs`/`README.md` collisions by hand.
For the foundation commit (wave 0) this does not arise — it IS the integration branch's first commit. Make wave-0 land on the integration branch and have every wave-1+ agent merge that branch in first.

### Per-agent contract (every implementation worktree)
1. Merge the integration branch in (gets foundation + prior waves).
2. Implement the pass/module + register in `passes.rs::default_passes()` (or `passes_for`, post option-gating) at the documented position (DWARF AFTER LibProtoPass; eh_frame/entry-disc AFTER LibProtoPass; callfixup AFTER LibProtoPass; addrtable DISABLED/commented like s1_strings).
3. Add the pass-level unit test (over vendored fixture bytes, the `s1_protos::tests` style) AND, where a `.sla` headline exists, the `kuna-console/tests/verify_*.rs` e2e modeled byte-for-byte on `verify_w11_elf_plt_names.rs` (same specs-absent early-return skip guard).
4. Run ALL THREE gates IN THE WORKTREE and paste the results into the PR/commit:
   - `make test` -> **675/675 PARITY OK**
   - `make test-stages` -> **158/158 PARITY OK**
   - `make rust-test` -> green
   - if the agent touched stages.toml/options: also `kuna catalog --check` green.
5. For s1-dwarf-1 (gimli): run the `cargo build` that locks gimli and COMMIT `Cargo.lock` (offline-gate safety).
6. Update `docs/analysis-port-log.md` (new "Increment N" section, established style) + the work-list row status, and `docs/missing-analyses.md` where the task reclassifies an entry.

### Sequential gated integration (the integrator's loop)
Integrate ONE worktree at a time onto the integration branch; after EACH merge re-run all three gates before merging the next. Order within a wave: merge the lowest-risk pure passes first (eh_frame, entry-disc, sourcelang, ruststring, the doc-only aggressive-disasm/operand-refs, dwarf-1, dwarf-2), then the commit-arm/engine-touching ones (arch-markers, callfixup), then wave-3 solos last. Because wave-1 passes are real-ELF-path-only and additive, `make test`/`make test-stages` stay structurally green; the re-gate after each is mainly to catch a `make rust-test` unit-count assertion that an extra discovered entry shifted (grep the suite for post-bootstrap function-COUNT assertions BEFORE merging eh_frame/entry-disc — these add functions like register_tm_clones/_start; update or scope any such assertion).

### Which tasks must be SOLO (no parallel worktree alongside)
- **engine-followups-1 (printer)** — the ONLY task that can move the 675/158 byte-parity oracles. Solo, instrumented (A/B strings-on/off to pin the exact render arm in printc.rs BEFORE editing), human-reviewed. If it forces a datatest re-baseline, that is a deliberate DIV — escalate to the human, do not silently `--save-baseline`.
- **engine-followups-2 (option-gating)** — restructures bootstrap commit timing + adds settable rows that break the stages.toml count test + touches the catalog drift-check. Solo; integrate after all passes are registered.
- **s1-dwarf-3 (ScopeLocal stack-var map)** — invasive p0_knowledge/database.rs wiring; do a SPIKE first to confirm the map-local seam is reachable from bootstrap without disturbing the XML path. If the spike fails, mark PARTIAL/deferred with an infeasible-at-tier note (parallel to FindNoReturnFunctionsAnalyzer) — do NOT force it.
- **s1-formatstring-B (decompile-loop)** — engine-driver change; gate the new behavior OFF by default so all three gates are unconditionally green. Solo-ish; needs formatstring-A merged.

### Which tasks need a HUMAN DECISION
- engine-followups-1: whether a datatest re-baseline is acceptable (DIV pin).
- engine-followups-2: option (a) put pass-gate ids in KUNA_OPTION_NAMES vs (b) console-only handling — affects catalog drift-check; pick per how strict the drift cross-check is.
- s1-dwarf-3 greenlight after the spike; s1-formatstring-B default-on vs off (recommend off, matching Ghidra setDefaultEnablement(false)).
- Any fixture that cannot be built in-env (ARM-Thumb linked exe; g++/-pg availability) — human builds off-host or the task ships unit-only with the e2e as a documented follow-up.

1. **engine-followups-1 (printer)** — THE risk. Touches `s9_emit/printc.rs`, on the 675-datatest + 158-stage byte-parity path. Mitigate: A/B instrument to pin the exact render arm BEFORE editing; guard the new behavior to readonly char-printable arrays only; verify `make test`/`make test-stages` byte-identical; if a re-baseline is forced, escalate to human (DIV pin) — never silent `--save-baseline`. Solo.
2. **engine-followups-2 (option-gating)** — restructures bootstrap commit TIMING and adds settable rows that break the stages.toml asserted-count test + must keep `kuna catalog --check` green. Real-ELF-only so 675/158 are structurally safe, but the shared codegen/console/CLI surface is invasive. Preserve the "commit AFTER read_loader_symbols" ordering invariant in the new IfcReadSymbols commit. Solo.
3. **arch-markers commit arm** — `set_variable` on a non-ARM language returns Err; the commit arm MUST swallow it as a no-op or every non-ARM ELF decompile regresses (real-ELF path; not the XML gates). Plus the ARM function-address LSB shift (odd entry addr) may make `load function` fail — verify by decompiling the linked fixture; if it fails, the function-symbol normalization is in-scope and raises difficulty.
4. **rust-test function-COUNT assertions** — eh-frame/entry-disc ADD discovered functions (register_tm_clones, _start, frame_dummy) on symboled binaries; grep for and update any post-bootstrap count assertion before merging.
5. **gimli offline-gate** — Cargo.lock must carry gimli before an offline gate run; commit the lock from dwarf-1's worktree.
6. **gimli type-cycle non-termination** (dwarf-2) — struct→ptr→struct cycles infinite-loop without the recursion cap; port `trackRecursion` (~depth 3).
7. **s1-dwarf-3 / s1-formatstring-B** — both touch invasive engine surfaces (database stack-scope / decompile driver); gate OFF / spike-then-defer rather than risk the gates. Everything else (eh-frame, entry-disc, sourcelang, ruststring, addrtable, dwarf-1, dwarf-2, callfixup, formatstring-A, the two doc-only tasks) is real-ELF-path-only and additive → structurally cannot move the 675/158 oracles; their only gate interaction is `make rust-test` staying green (new unit tests).

ELF-only guard (`matches!(ctx.file.format(), object::BinaryFormat::Elf)`), never fails (return empty `AnalysisOutput` on any parse anomaly — additive contract).

**Faithful logic (`scan_eh_frame_starts`):**
1. Get the `.eh_frame` section via `ctx.file.section_by_name(".eh_frame")` (use the same `ObjectSection` import as s1_strings); read `sec.address()` (section vma — needed for nothing here since pcrel is relative to the *field* addr) and `sec.data()` (the bytes). Skip if absent/empty. (Mirror `GccExceptionAnalyzer.canAnalyze` `.eh_frame` block check.)
2. Walk the section as a sequence of CFI records, exactly as `EhFrameSection.analyzeSection`:177 + `Cie/FrameDescriptionEntry`: at each record offset `o`, read `length = u32-le-at(o)` (`createFdeLength`). If `length == 0` → end-of-frame, stop. If `length == 0xffffffff` → 64-bit extended length record; SCOPE: log-skip these (Ghidra itself throws "ExtLength not completely implemented", Cie.java:520 / FDE :499) — read the 8-byte length and skip the record. Next-record offset = `o + 4 + length`.
3. Read `cieId = u32-le-at(o+4)` (`createCiePointer`/`processCieId`). `cieId == 0` ⇒ this record is a **CIE** (`.eh_frame` convention; note: differs from `.debug_frame` where 0xffffffff marks the CIE — we only do `.eh_frame`). Parse the CIE to extract the FDE pcBegin **encoding byte**: walk version(u8) / augmentation-string(NUL-terminated) / [if v≥4: ptrsize u8, segsize u8] / code-align(ULEB) / data-align(SLEB) / return-addr-reg(v1: u8, else ULEB) / if aug starts with 'z': aug-data-len(ULEB) + aug-data bytes; within aug-data, walk the aug-string chars after 'z' — for each 'R' the next aug-data byte is `fdeEncoding`; 'L' consumes 1 byte (lsda enc, ignore); 'P' consumes 1 enc byte + a personality pointer of that enc's size (decode-and-skip); 'S' consumes 0. Store `fdeEncoding` keyed by CIE offset `o` (faithful to `Cie.processAugmentationInfo`:559-609). Default encoding 0 = DW_EH_PE_absptr if no 'R'.
4. `cieId != 0` ⇒ **FDE**. Its CIE is at `cie_off = (o+4) - cieId` (`createCiePointer`:225 relative ref). Look up that CIE's `fdeEncoding`. The pcBegin field starts at `o + 8`. Decode it per the encoding (see decoder below); push the resulting vma to entries. Then continue to next record at `o + 4 + length` (do NOT need to parse pcRange/augmentation — we only want the start, the byproduct of `CreateFunctionCmd(pcBeginAddr)`).

**The DW_EH_PE decoder (faithful to DwarfDecoderFactory + AbstractDwarfEHDecoder.resolveRelativeOffset):** given `(encoding: u8, field_vma: u64, bytes, field_off, ctx.arch)`:
- format = enc & 0x0F, appl = enc & 0x70, indirect = enc & 0x80. SCOPE: `indirect` is not resolvable without reading the runtime relocated pointer — Ghidra's `ptrval` deref; document as LOSS, skip the FDE if indirect (rare for FDE pcBegin; never in the fixtures).
- raw value by format: 0x00 absptr → read ptr-size (`ctx.arch.types().get_size_of_pointer()`, 8 for x86-64) little-endian; 0x01 uleb128; 0x02 udata2 (u16); 0x03/0x0b udata4/sdata4 (4 bytes, signed for 0x0b); 0x04/0x0c udata8/sdata8 (8 bytes); 0x09 sleb128; 0x0a sdata2. Sign-extend the signed formats.
- apply by `appl`: 0x10 DW_EH_PE_pcrel → `field_vma + raw` (wrapping, `resolveRelativeOffset`:295-297); 0x30 DW_EH_PE_datarel → `eh_frame_section_vma + raw`; 0x00 absptr → `raw` as-is (the gcc/non-PIE absolute case; image-base adj is 0 here because kuna loads at the file's own vmas — `ObjectLoadImage` does no rebase, so the AbstractDwarfEHDecoder image-base adjustment is identically 0; document this). Other appl modes (funcrel/aligned/textrel) → SCOPE: not used for FDE pcBegin, treat as absptr / skip.
- For the fixtures the path is exactly `pcrel|sdata4` (0x1b): `field_vma + (i32 from 4 le bytes)`.

**Provide the testable seam:** a free `fn scan_eh_frame_starts(file: &object::File) -> Vec<u64>` (taking just the file for the unit test; the absptr ptr-size can default to 8 for the test, or thread an `Option<u32> ptr_size` — fixtures are all sdata4/pcrel so ptr-size is unused in the test). Dedup the returned vec.

**Risks.** **Faithfulness risks:**

**Approach.** ## What is genuinely a gap vs inherited (read this first — it is the crux)

There are THREE distinct things the prompt conflates; pin them precisely:

1. **kuna's S2 jump-table CORE (`JumpTable::recoverAddresses`)** — INHERITED 🟡. 2. **`AddressTableAnalyzer` (this task's real subject)** — a GAP, but a *small, low-payoff* one. It is NOT switch recovery. **Risks.** ## Faithfulness / payoff risks

- **Low decompiler payoff, real false-positive risk.** This is exactly why Ghidra ships it off by default. A pointer-run scanner over .rodata/.data over-accepts (any coincidental run of in-range aligned values reads as a "table"). Mitigate with the min-run threshold + the executable-target check + the string guard; pin the test to one known table address rather than asserting an exact total table count.

- **The classification is the deliverable as much as the code.** The biggest risk is an implementer "porting AddressTableAnalyzer" and accidentally re-implementing switch recovery (item 1, inherited) or trying to wire roadmap #9 (item 3, engine S2). Both would (a) duplicate inherited engine logic and (b) the #9 path touches the action restart group + a W4 SEAM and would put `make test`/`make rust-test` at risk. The brief pins these as out-of-scope; the reviewer must enforce it.

- **Fixture determinism.** The emitted table VMA and element addresses depend on the exact gcc build. The fixture MUST be checked in (not built at test time), and the expected table VMA pinned as a const read from `objdump -d`/`readelf -x .rodata` at fixture-creation time. Re-running gcc on a different toolchain would shift addresses and break the test — document the exact build command in tests/fixtures/README.md alongside the existing fixture provenance notes.

- **Parity-gate risk: low for the pass itself** (pure AnalysisOutput producer, ELF-path-only binding, no engine/printer/type-factory change, commits via the existing SymKind::Data arm), but **note** the same shadowing hazard that disabled `s1_strings`: a `SymKind::Data` symbol planted at a table address could mask other rendering. This is why the pass is disabled-by-default and emits sparse data labels rather than aggressively typing memory. If a future agent enables it, A/B the decompiled output of the switch fixture's function (before/after) to confirm no regression in the switch's own (engine-recovered) case rendering.

### Why it does not fit (read the source, this is faithful, not a guess)
AIF is the polar opposite of every pass kuna has ported so far. The ported passes (`noreturn`, `s1_protos`, `s1_demangle`, `elf_plt`) are pure functions over `object::File` + `ObjectLoadImage` + `Architecture` (the `AnalysisCtx` in `decompiler/crates/kuna-analysis/src/pass.rs:103-110`): they read symbol/section tables and emit additive `AnalysisOutput` facts. AIF reads none of those. It is a *post-disassembly, whole-program, iterative* analyzer that:
1. Requires a fully populated `Listing` (disassembled instructions) and `FunctionManager` with >=20 functions ALREADY found (`AggressiveInstructionFinderAnalyzer.java:97-102`) — kuna's analysis tier runs *before* any decompilation; there is no Listing and no global function-discovery (function discovery itself is the still-open `s1-entry-disc` gap, `docs/analysis-port-log.md:124`).
2. Builds a function-start byte-fingerprint histogram via `SleighDebugLogger`/`getInstructionMask`/`getMaskedBytes` (`:130-164`) and accepts a gap candidate only if its masked-byte prefix matches a fingerprint seen >=4 times with a matching disassembly context (`:273-284`). kuna has NO instruction-mask / SleighDebugLogger machinery (`grep -rn "SleighDebugLogger\|getInstructionMask\|PseudoDisassembler\|followSubFlows" decompiler/` returns 0 hits outside cpp anchors — confirmed).
3. Speculatively disassembles undefined gaps with `PseudoDisassembler.followSubFlows` + `checkValidSubroutine` (`:296-363`), validating with heuristics (calls/jumps into existing code "add info", `numInstr>2`, body has no defined data, ARM body-locality/back-branch checks `:451-479`) and then commits real code with `DisassembleCommand` (`:380`). kuna has no recursive-descent disassembler, no `PseudoDisassembler`, no `Listing`, no `DisassembleCommand`-equivalent at this tier.

### Why it is low-value even if it were feasible
- Ghidra ships it `setDefaultEnablement(false)` and warns in its own DESCRIPTION (`:52-54`): "This should not be run unless good code has already been found. YOU MUST CHECK THE RESULTS, IT MAY CREATE A LOT OF BAD CODE!". It is a last-resort, opt-in, error-prone gap filler.

For a tier that already receives the entry, this folds entirely into entry-point discovery: the value AIF adds (new entries) is the same value `s1-entry-disc`/`EntryPointAnalyzer` + `s1-eh-frame` (FDE starts) deliver, by sounder means (symbol tables, `.eh_frame` FDEs, relocation/call targets) — without speculative disassembly. ### Why splitting is infeasible at the kuna-analysis tier (the core finding)
`RustStringAnalyzer` does NOT scan bytes. It iterates `DefinedStringIterator.forProgram` (already-defined string Data objects) and, for each, calls `getMaxStringLength` = distance from the string start to **the next reference destination** (`ReferenceManager.getReferenceDestinationIterator`). Rust `&str` literals are stored as a contiguous blob in `.rodata` with NO NUL separators (VERIFIED in the fixture: "HelloRust" and "AnotherStringLiteral" are byte-adjacent); the only thing marking each slice boundary is a code reference (a PC-relative `lea` of `ptr+len`) into the blob interior. The analyzer relies on the post-disassembly `ReferenceManager` being populated with those interior destinations, then splits the over-long string at each. The kuna-analysis tier sees only the parsed `object::File` + load image — there is no disassembled listing, no defined-string data, and no reference manager (the same wall that makes `FindNoReturnFunctionsAnalyzer` and `EntryPointAnalyzer` infeasible here, per noreturn.rs:9-15 and analysis-port-log.md:128). I checked whether PIE relocations could substitute for references: the `R_X86_64_RELATIVE` addends point at code/data, NOT into the `.rodata` string range — slice pointers are inline PC-relative immediates in `.text`, invisible without decoding. So the boundary information simply is not available pre-decompile.

Additionally, even if boundaries were known, the same printer-shadowing problem that disabled `s1-strings` (passes.rs:38-44: a named `char[N]` symbol SHADOWS the literal in kuna's printer) applies — so emitting `StringFact`s here would not render slices anyway. This is a strict superset of the deferred `s1-strings` blocker.

## Sub-item (1) — PRINTER CHANGE to re-enable s1-strings

**Goal:** make kuna's C printer render a constant pointer to a readonly `char[N]` SYMBOL as the string literal (Ghidra behavior), so `StringLiteralPass` and `LibProtoPass` coexist. Today (per `docs/analysis-port-log.md` Increment 3) enabling the strings pass plants a typelocked `char[N]` data symbol at e.g. 0x400915, and kuna renders the call arg as the symbol NAME `s_400915` instead of `"Username: "` — the named global shadows the literal path.

**Root-cause to confirm first (READ before editing):** The literal path `push_ptr_char_constant_ir` (`printc.rs:6179-6228`) is reached only from the constant pointer arm of `push_vn_explicit_ir` (`printc.rs:5204-5258`), and it is gated ONLY on `arch.symboltab.is_read_only(...)` (line 6211) — NOT on symbol presence. So `push_ptr_char_constant_ir` itself would still fire. The shadowing therefore happens UPSTREAM of this arm: planting the typelocked `char[N]` symbol causes type propagation / the symbol-reference markup (`Funcdata::link_symbol_reference`) to turn the constant into a symbol-bound reference, so by render time the value arrives through the SPACEBASE/PTRSUB symbol-name arm (`printc.rs:5779-5885`, the `op_ptrsub_ir` SPACEBASE case) or the HighVariable-bound-name arm (`printc.rs:5318-5503`), which emit the bare symbol name and never consult the readonly-char literal path. The implementer's FIRST job is to instrument an A/B run (strings ON vs OFF over fauxware `main`) and pin EXACTLY which render arm produces `s_400915` — do not assume; the fix differs per arm. Likely it is the global-symbol-name arm reached after the char[N] symbol becomes the read-facing type.

**Faithful fix (mirror C++ `PrintC::pushConstant`/`pushSymbol`):** In the identified arm, before emitting the bare symbol name, add the Ghidra check: if the bound/covering Symbol's type is a `char`-printable array (`is_char_print()` on the array element) AND the symbol's address is readonly (`is_read_only`), route through `print_character_constant`/`push_ptr_char_constant_ir` to emit the quoted literal instead of the name. This is exactly what upstream does — a pointer to a readonly char-array data object prints as the literal, the data symbol and literal coexist. Keep it tightly guarded (only char-printable readonly arrays) so every other symbol render is byte-unchanged.

**Then:** flip `passes.rs::default_passes` to include `Box::new(crate::s1_strings::StringLiteralPass { min_len: 5 })` (uncomment line 44) and update the doc comments + `docs/analysis-port-log.md` Increment 3 (it currently documents the disable as deliberate). Add an A/B test asserting the literal renders with strings ON.

**SCOPE/LOSS:** purely a render coexistence fix; the strings pass logic is unchanged. If the A/B shows the literal still comes from libproto's `char*` typing (not the planted symbol) and the planted symbol is genuinely inert, the lighter alternative is to skip planting a symbol where the literal already renders — but the brief's intent is the printer change, so prefer teaching the arm to prefer the literal.

## Sub-item (2) — PER-RUN OPTION GATING of analysis passes (conflict #4) ✅ DONE (analysis-port-log.md Increment 13)

**Goal (achieved):** make each pass id (`noreturn_known`, `libproto`, `strings`, `entry_disc`, `arm_markers`, `dwarf`, `callfixup`, `addrtable`) a settable assertion so `kuna catalog` lists it and `kuna decompile --option <id> on|off` toggles whether its facts are committed. Implemented via option (a) — names in `KUNA_OPTION_NAMES` + a per-id `analysis_*` bool on `Architecture`; commit deferred from `bootstrap_from_elf` to `IfcReadSymbols`; `build_script` emits `option …` before `read symbols`. Default-on (except `addrtable` off). See the Increment 13 writeup for the full shape.

**The ordering bug (confirmed):** CLI `build_script` (`kuna-cli/src/decompile.rs:48-55`) emits `load file` → `read symbols` → `option ...`. But the analysis commit runs inside `bootstrap_from_elf` (`kuna-console/src/engine.rs:490-520`, at `load file`), BEFORE any `option` line arrives. So a gate option set on the command line is a no-op as wired.

**Resolution (the deferred plan in analysis-port-log.md:179-191):**
1. In `bootstrap_from_elf` (`engine.rs:486-520`), STOP committing eagerly. Instead run `run_default_analyses` and STASH the merged `AnalysisOutput` (and the `code_space` Rc) on the `ConsoleProgram` (new field) — do NOT call `commit_analysis_output` here. (Keep readonly markup where it is; it is not a gated pass.)
2. Move the commit into `IfcReadSymbols::execute` (`ifacedecomp.rs:970-985`, currently a no-op success). It runs AFTER `load file`. But note `read symbols` is still emitted BEFORE `option` in build_script — so ALSO reorder build_script to emit `option` lines BEFORE `read symbols` (move the loop at decompile.rs:53-55 above line 52). Then `IfcReadSymbols` reads the now-set per-pass gate flags and commits only enabled passes' facts.
3. Per-pass gating granularity: stash the output PER PASS (e.g. `Vec<(pass_id, AnalysisOutput)>` rather than one merged output) so `IfcReadSymbols` can drop a disabled pass's facts. This requires `run_default_analyses` to return per-pass outputs (add a sibling fn keeping the per-pass split; `run_analyses` already iterates passes — return `Vec<(&'static str, AnalysisOutput)>`).
4. Register each pass id in `stages.toml` as a `[[settable]]` row (values `on|off`, default `on` to stay faithful to Ghidra default-on analyzers and parity-safe). These are a NEW settable category — they do NOT map to an engine `live_field`; they gate the console commit. So the codegen `live_field`/`live_true`/`live_false` mechanism does not apply directly. Two options: (a) add the ids to `KUNA_OPTION_NAMES` and route them in `IfcOption` (`ifacedecomp.rs:754-762`) to a NEW per-pass-gate flag store on the program (not `set_kuna_option`, which writes engine live flags); or (b) keep them out of the engine option registry and handle them entirely console-side in `IfcOption` (recognize the pass-gate names, write the gate map, return success) — (b) is cleaner and avoids growing the engine option set. Either way, `kuna catalog` parses `stage catalog` JSON, so the settable rows must appear there; verify `kuna catalog --check` (drift cross-check against `KUNA_OPTION_NAMES`) still passes — choose (a) if the drift-check requires the names in `KUNA_OPTION_NAMES`, else (b) plus a catalog/drift adjustment.

**SCOPE:** wiring + reorder + registration only; pass logic unchanged. Default-on keeps current behavior, so gates should hold if the eager→deferred move is faithful (commit still runs, just later).

## Sub-item (3) — NO-RETURN × DEMANGLE cross-pass seam

**Goal:** a mangled no-return C++ symbol (e.g. `_ZSt9terminatev` → installed as `std::terminate`) must be found and marked no-return. Today it is missed.

**The seam (confirmed):** `noreturn.rs::scan_noreturn` (`s1_loader/noreturn.rs:102-126`) scans the RAW `object::File` symbols, applies only `strip_version`, matches the list (the namespace guard already accepts `std` and the matcher already tests the mangled `ZSt9terminatev` base — see existing tests noreturn.rs:187-188), and pushes the RAW name into `out.noreturn` (line 122). But the funcsym is INSTALLED under the demangled name `std::terminate` (via `loadimage_object.rs::demangle_funcsym_name`). The commit (`engine.rs:603-611`) does `query_global_function(name)` with the RAW name → miss (it queries the global scope only, and the symbol lives in the `std` namespace scope anyway).

**Fix (preferred — emit the installed name):** in `scan_noreturn`, after a name matches the list, run it through `crate::s1_demangle::demangle_name(raw)` and push the DEMANGLED form (`std::terminate`) when demangling succeeds, else the raw name — so `out.noreturn` carries exactly what was installed. Then the commit must resolve a `::`-qualified name across scopes: replace `query_global_function(name)` at `engine.rs:607` with an address/qualified-name cross-scope lookup. Two faithful routes:
- (a) Switch the commit to resolve by ADDRESS instead of name: have the noreturn pass emit `(addr)` (or `(addr, name)`) and use `Database::find_function_across_scopes(&addr)` (`database.rs:2701`) → `set_function_no_return(sid, true)`. This is the most robust (immune to demangle spelling) and reuses the cross-scope helper the demangle increment already added (database.rs:2701-2744). It requires extending the `noreturn` fact from `Vec<String>` to carry the address (the scan already has `sym.address()`).
- (b) Keep name-based but add a `query_function_across_scopes_by_name` and feed the demangled qualified name. Simpler diff but spelling-fragile (cpp_demangle vs c++filt `__cxx11` divergence noted in s1_demangle docs).

Prefer (a): it is spelling-independent and matches how the demangle increment already solved call resolution (across-scope by address). Update `AnalysisOutput.noreturn` shape (and `noreturn.rs`, `passes.rs` doc), and `commit_analysis_output` step 3 (`engine.rs:603-611`).

**SCOPE/LOSS:** small, faithful; resolves the documented seam (analysis-port-log.md:270-276). Address-based resolution is additive and idempotent like the rest of the commit.

**Risks.** (1) PRINTER CHANGE is the highest-risk item — it touches `s9_emit/printc.rs`, which is on the 675-datatest + 158-stage parity path. Any over-broad change to a symbol-render arm will perturb the XML datatest output (the corpus has many global/array symbol renders). The fix MUST be guarded to fire ONLY for a readonly char-printable array symbol, and the implementer must verify `make test`/`make test-stages` are byte-identical. The real risk is mis-identifying WHICH arm produces `s_400915` (the brief identifies candidates: the HighVariable-bound-name arm `printc.rs:5318-5503` and the SPACEBASE PTRSUB arm `printc.rs:5779-5885`); guessing wrong wastes the worktree. Mitigation: instrument an A/B (strings ON/OFF) over fauxware first and pin the exact arm. There is also a possibility the planted symbol is genuinely inert and the literal already comes from libproto's char* typing — in which case the "shadowing" only appears for strings NOT covered by a libproto'd call; confirm the failing case before coding.

(2) PER-RUN GATING risk: the eager→deferred commit move changes WHEN facts land relative to `read_loader_symbols` and readonly markup; the current ordering comment at `engine.rs:517-520` ("AFTER read_loader_symbols so no-return name resolution finds the just-installed FunctionSymbols") must be preserved in the new `IfcReadSymbols` commit. Reordering `option` before `read symbols` in build_script could perturb other option semantics — audit that no existing option depends on running after `read symbols`. The catalog drift-check (`kuna catalog --check`) cross-checks `KUNA_OPTION_NAMES`; adding pass-gate names there vs handling them console-only must keep the check green. New settable rows must keep the asserted counts in stages.toml tests updated (the header asserts group=39/substage=40/surface=90/settable=23 — adding settables breaks that count test unless updated).

(3) NO-RETURN×DEMANGLE risk is lowest. If route (b) is chosen, the cpp_demangle vs c++filt spelling divergence (s1_demangle docs:54-58) could still cause a miss for `__cxx11`-class names — route (a) by-address avoids this entirely. Changing the `AnalysisOutput.noreturn` field shape ripples to `pass.rs`, `noreturn.rs`, `passes.rs` doc, and `commit_analysis_output`; keep it minimal. End-to-end test needs a g++ fixture (may not be buildable in CI) — fall back to a unit-level scan+resolve assertion using the existing cpp_mangled fixture or a synthetic object if g++ is unavailable. All three sub-items are real-ELF-path bound, so the XML datatest oracle is structurally untouched EXCEPT sub-item (1), which is the one that genuinely risks the 675/158 gates.

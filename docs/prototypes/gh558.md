# Prototype: fixing Ghidra GH-558 through the kuna stage model

**Issue:** [NationalSecurityAgency/ghidra#558](https://github.com/NationalSecurityAgency/ghidra/issues/558)
— "Don't change conditions to equivalent expressions during decompilation."
Open since 2019, still confirmed on 11.3/12.x in 2025-2026; reproduced in the PHADE
issue dataset against Ghidra 12.1 (kuna's vendored revision is 12.1.1/cef869af).

**Claim being tested:** the kuna stage model (`docs/stage-model.md`) says decompiler
issues of this class are not bugs but **unexposed sub-stage decisions** — fix them by
splitting the decision into named, finer-grained stages controlled by durable P0
assertions, not by patching behavior. GH-558 was chosen because it is pure
representation policy: output is semantically *correct* both ways, so there is no
"bug" to accidentally fix — any improvement must come from exposing the decision.

## The issue, in stage-model terms

GH-558 bundles two complaints:

1. **Headline:** `x <= 8` decompiles as `x < 9`. The simplifier canonicalizes every
   `LESSEQUAL`-with-constant into `LESS` with constant±1 so Band-B analyses see one
   canonical comparison form — and that analysis-canonical artifact leaks through to
   the rendered C. A commenter (hwrobel, 2025) notes the constant rewrite also breaks
   enum/flag display: a `2^n` source constant becomes `2^n - 1`.
   *Old-taxonomy mapping (PHADE):* stage 05 Simplify (+11, 17).
   *Stage model:* an **S3 "simplification quiescence" decision** (§7.1) destroying a
   fact that **S9** needs — the constant that exists in the binary.
2. **Secondary** (what the dataset repro keys on): `p->r[i]` renders as
   `*(p->r + i)` / `ppuVar1 = p->r + iVar2`. Upstream `PrintC::opPtradd` uses array
   notation only when the pointer value is consumed by a load/store in the same
   expression; a standalone `PTRADD` falls back to `+`.
   *Stage model:* a **LATENT S9 "literal/format policy" decision** (§10) — hardcoded,
   no override surface.

## What was built

### 1. `canonicalcompare` / `presentcompare`: splitting the comparison-form decision

- **Provenance at the canonicalization primitive.** `Funcdata::replaceLessequal`
  (funcdata_op.cc) is the single primitive implementing `V <= c => V < c+1`. It now
  marks the rewritten op with a new `PcodeOp::addlflags` bit (`canonical_lessequal`,
  0x1000, accessors in op.hh). The principle: *a Band-B canonicalization that crosses
  the boundary to S9 must be reversible* — provenance is what makes the sub-stage
  split possible at all.
- **The Band-B side gets a name.** `RuleIntLessEqual` moves from the monolithic
  `"analysis"` group (132 rules) to a new `"canonicalcompare"` group, added to all
  five pipeline variants (`decompile`/`jumptable`/`normalize`/`paramid`/`register`) so
  default behavior is unchanged. The canonicalization is now an independently
  selectable pipeline component.
- **The presentation side becomes a new sub-stage.** `ActionPresentCompareForm`
  (kuna-owned `decompiler/cpp/kuna_compareform.{hh,cc}`, group `"presentcompare"`,
  `decompile` variant only) inverts marked ops — `V < c+1 => V <= c`, with
  re-validation and the mirrored overflow guards — restoring the source form,
  including `copySymbol` so data-type/symbol info on the constant survives.
- **P0 control:** `option compareform canonical|original` (`OptionCompareForm`,
  ElementId 4000; kuna ids live at 4000+, upstream max is ~290), default `canonical`
  = byte-identical upstream output.

### 2. `arraynotation`: exposing the pointer-notation decision

`PrintC::opPtradd` gains a third mode: when `option arraynotation on` is set
(`OptionArrayNotation`, kuna-owned `decompiler/cpp/kuna_arraynotation.{hh,cc}`,
ElementId 4001), a standalone `PTRADD` renders as `&base[index]` — reusing the
`addressof`+`subscript` RPN nesting already proven by `opPtrsub`'s `&(...)->field`
form. Default `off` is byte-identical upstream output.

### 3. Testcases: `tests/stages/`

New kuna-owned datatest family for issue-derived stage-model testcases
(`make test-stages`, baseline `docs/baseline-stages.json`, never touches the
upstream baseline). Each test decompiles **twice in one script** — default pipeline
(must reproduce the issue) then with the P0 assertion applied (must show the fix):

- `gh558-compareform.xml` — 14 hand-assembled x86-64 bytes for
  `int f(int x){ if (x<=8) return 1; return 0; }`:
  pass 1 asserts `if (x < 9)` (bug), pass 2 asserts `if (x <= 8)` (fix).
- `gh558-arraynotation.xml` — the `foo` function from the issue's **own attached
  binary** (foo.zip, gcc 13.3 -O3): pass 1 asserts `= p->r + ` (bug, identical to
  the report), pass 2 asserts `= &p->r[` (the rendering the issue praised in
  Hex-Rays/Binary Ninja).

All 4 assertions pass; upstream parity stays at **PARITY OK** (204/204 unit tests,
675/675 datatest assertions) in the default configuration.

## The key discovery: the decision was smeared, not encapsulated

The plan assumed the canonicalization lived in `RuleIntLessEqual` (the rule pool) —
the obvious, toggleable place. **Empirically false for the very first testcase.**
Disabling the rule entirely (`option togglerule intlessequal off`) still produced
`x < 9`, because `Funcdata::replaceLessequal` is also called from the **branch-flip
machinery** — `opFlipInPlaceExecute` and `opNormalizeFlip` — which canonicalizes
comparisons while flipping branch senses during **block structuring**
(`BlockIf::preferComplement` ← `ActionPreferComplement`,
`BlockBasic::finalTransform` ← `ActionStructureTransform`), as late as the
post-merge, post-structure passes.

Two consequences, both validating the stage model's framing:

1. **The "same" decision fires in three places across two stages** (Band-B
   simplification and S7/S8 structuring), invisible to every existing control
   surface. Per-rule toggles — the only knob upstream offers — cannot reach two of
   the three sites. This is exactly what the model calls a LATENT sub-stage: a
   decision that exists in the code but has no name and no override surface.
2. **Placement of the inverse decision is forced by the feedback structure.** The
   first implementation registered the inverse as a cleanup-pool rule — dead wrong:
   the cleanup pool runs *before* the final flip sites, so its output was re-coupled
   to the structuring stage's canonicalizations. The working placement is a discrete
   action after the last flip pass and before prototype/naming/cast fixation — i.e.
   the model's S8→S9 boundary is a *real, physical* program point in
   `universalAction`, and the sub-stage had to be placed exactly there.

## Experiments

Question: what does the rest of the pipeline actually *depend on* from this
canonicalization? (This is the difference between "split the stage" and "just turn
the rule off".)

- **(a) `compareform original` forced globally over the 83 upstream datatests:**
  **12 of 675 assertions change (1.8%); all 83 files execute cleanly** — no errors,
  no structure loss; the 12 are text-form mismatches in tests whose expected regex
  encodes the canonical `<` form (e.g. *Boolean thru Less-than*, *Promotion on
  compare*, *For-loop with skip*, *If/Switch*). Restoring the original form is
  purely a surface change.
- **(b) `canonicalcompare` excluded from the decompile pipeline (canonicalization
  never fires in the rule pool):** **9 of 675 assertions change; all files execute
  cleanly — but the changed set is different from (a)**: only in (b) do *Bitfields
  #8/#17* and *Boolean thru Less-than #2* change (downstream rules keyed on the
  canonical `INT_LESS` shape simplify differently when fed `LESSEQUAL`), while
  (a)-only changes (*Else-if*, *For-loop with skip*, *Inline target*, *If/Switch*,
  *Promotion on compare*) are pure rendering. **This asymmetry is the empirical
  argument for the split**: disabling the canonicalization perturbs *analysis*;
  restoring at presentation perturbs only *text*. "Turn the rule off" and "present
  the original form" are different decisions — the stage model's claim that they
  belong to different sub-stages is observable in the test suite. (Note also that
  excluding the group does **not** remove canonicalization entirely — the
  branch-flip sites still fire, which is why (b) changes only 9 assertions and not
  every comparison-bearing test.)
- **(c) Structural diff of the testcase outputs across the option:** only the
  comparison operator/constant (and pointer notation in testcase 2) change; block
  structure, variable naming, and types are identical.
- **(d) Enum sub-case:** with an enum-typed parameter, the comparison renders as
  `(int4)x < 9` vs `(int4)x <= 8` under the option — the *constant value* from the
  binary is preserved, which is the substance of the enum complaint (a symbol/equate
  for 8 can now resolve; under canonical form it cannot, since the program contains
  no 9). Full enum-token rendering (`x <= BPP_8`) additionally requires the enum
  type to propagate into the comparison constant, which Ghidra's type lattice does
  not do for these compare shapes — an independent S5 propagation decision, noted
  as future work, not papered over here.

## Honest assessment: did we fix a "bug"?

**No decompiler behavior was corrected.** Both renderings are semantically correct;
upstream's canonical form is byte-for-byte preserved as the default and the full
upstream test suite passes unchanged. Every line of new behavior is gated behind two
new P0 assertions (`compareform`, `arraynotation`) that default off. What changed
structurally:

- one hidden, three-sited decision got a name (`canonicalcompare`), provenance, and
  an inverse (`presentcompare`) at a stage boundary that turned out to be physically
  real;
- one hardcoded rendering decision got a parameter (`arraynotation`).

That is the stage-model thesis operating as designed. The one caveat worth recording:
the *granularity* of both assertions is currently whole-function/global (set via
`option`, consulted at run time). The model ultimately wants per-anchor assertions
(e.g. "this comparison stays original; that one stays canonical") — the provenance
bit makes per-op granularity straightforward (the anchor exists), but the assertion
store surface for per-op anchors (DynamicHash-keyed, like `UnionFacetSymbol`) is
future work (roadmap §16.1).

## The index shapes (arrayidx2.py)

A sized pointee makes `p[k]` step by the aggregate's width, so an index respells
an offset.  Two shapes, 41 sites:

  member-then-index  p->d_name[k]      31 sites, all dirent::d_name, ALL BETTER
  index-then-member  p[k].member k!=0  10 sites, 4 TRUE and 6 MIS-NAMED

`p[0].member` is excluded: index 0 on a by-value array (`stat v[2]`) is an
ordinary element and carries no claim beyond the declaration.  So is
`p[k].field_0xNN` -- that is the neutral offset form, makes no member claim, and
is what `opaque` prints too; it accounts for the difference between the 15 raw
matches and the 10 counted here (5 of them are the diffutils reads the
reserved-row rule keeps neutral).

  e2fsprogs/e2fsck init_resource_track @0x339d0     9 sites, 4 true / 5 misnamed
    a0 is `timeval *` from gettimeofday; really `struct resource_track *`
    whose first THREE members are timevals.
      a0[1].tv_sec/tv_usec, a0[2].tv_sec/tv_usec   TRUE (user_start, system_start)
      a0[3].tv_sec                                 really brk_start

## The reserved rows, and why they are gone

Before the rule was added, `stat::__pad0`, `stat::__glibc_reserved`,
`_IO_FILE::__pad5` and `_IO_FILE::_unused2` were carried and fired 28 times:

  19  padding copies inside a whole-struct assignment.  Carries no information:
      `v12.__glibc_reserved[0] = v13.__glibc_reserved[0]` says exactly what
      `v12._120_8_ = v13._120_8_` says.
      (coreutils/stat 7, findutils/find 4, tar/tar 4, dpkg-statoverride 4)
   8  LIES.  diffutils/diff @0x8e70: v15 points at `file_data.stat`, so the
      enclosing struct's own `desc` and `name` sit at -1 index plus 0x80/0x88,
      inside __glibc_reserved:
        -   if ((int)v15[-1].__glibc_reserved[1] != -1)     /* cmp.file[N].desc */
        -     v9 = (char *)v15[-1].__glibc_reserved[2];     /* cmp.file[N].name */
        +   if (*(int *)&v15[-1].field_0x80 != -1)
        +     v9 = *(char **)&v15[-1].field_0x88;
   1  an address computation the name made harder to read.  grep/grep:
        -   v21 = (long)v32.__glibc_reserved + (long)v10 * 4 + -0x78;
        +   v21 = (long)&v32.st_dev + (long)v10 * 4;

## Three printer respellings, all pre-existing behaviour surfaced by a pointee
## width or signedness change

  1. `*(unsigned int *)&v10[3] & 0xf000` -> `v10[3] & 0xf000` when the pointee
     goes `long` -> `unsigned long`.  Reproduces on main with no libctypes:
       int f_u(unsigned long *p){ return (*(unsigned int *)&p[3] & 0xf000) == 0x4000; }
       int f_s(long *p)         { return (*(unsigned int *)&p[3] & 0xf000) == 0x4000; }
       int4 f_u(uint8 *p) { return (int4)((p[3] & 0xf000) == 0x4000); }
       int4 f_s(int8 *p)  { return (int4)((*(uint4 *)&p[3] & 0xf000) == 0x4000); }
  2. `*(char *)&vN[4]` -> `(char)vN[4]`, same class.
  3. e2fsck @0x61c00, where a WIDER pointee makes an increment explicit:
       -   v19 = (unsigned int *)&v18.field_0x28;   v2 = &v19[1];   *v20 = *v19;
       +   v19 = &v18.st_rdev;    v2 = (uint8 *)((int8)v19 + 4);   *v20 = (int4)*v19;
     (`st_rdev` is 8 bytes wide, the loop copies 4-byte elements.)  Less
     readable, and a consequence of the slot-reuse shape below.

## Two shapes the field names get wrong, beyond the index hazard

  SLOT REUSE.  e2fsck `ext2fs_add_journal_inode3` @0x61c00 has both a
  `struct stat` (for `fstat`) and a `struct ext2_inode`, and the compiler gives
  them one stack slot.  kuna types that slot `stat` in BOTH arms -- the
  declaration is already wrong under `opaque` -- but `opaque` reads the inode
  half as neutral offsets and `glibc` names them:
        -   if (v18._28_4_)          +   if (v18.st_uid)          /* i_gid */
        -   v18._26_2_ = 1;          +   v18.st_mode._2_2_ = 1;   /* i_links_count */
        -   v18._0_2_ = 0x8180;      +   v18.st_dev._0_2_ = 0x8180;  /* i_mode */
        -   v18._32_4_ |= 0x80000;   +   v18.st_gid |= 0x80000;   /* i_flags */

  BY-VALUE LOSS.  shadow/useradd `main` @0x6480 loses its recovered 144-byte
  `stat` stack symbol at -0x218: a neighbouring char[16] at -0x268 grows to
  char[128] and swallows it.  43 `variables[]` rows in both arms; the `stat` row
  is one of them under `opaque` and none of them under `glibc`.  Two other
  useradd functions (0xfde0, 0x16520) gain one, which is where the net +2 in the
  by-value count comes from.  decbench scores this function 0.08064516129032258
  with {tp:5, fp:4, fn:53, decomp_vars:43} in BOTH arms, so the metric cannot
  see it.

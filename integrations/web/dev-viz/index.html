      04 / measurements

      Recorded benchmark changes

      These feature records compare graph edit distance (GED) before and after a change. Lower means the measured control-flow graph is closer to the source’s graph. Zero means matching graph structure, not identical source code or proof of correctness.

      Gray bars show the earlier measurement; red bars show the later one. Each row links to the feature’s recorded result for one function. These examples do not measure overall decompiler quality.

      05 / method

      How changes are tested

      Coding agents can select problems, implement changes, and run checks. People set the direction and review results. The benchmark loop records test cases, measurements, and the reasons for a change.

      1. 01

        Find

        Find functions with poor output through benchmarks, RE sessions, or issue reports.

      2. 02

        Reproduce

        Check the problem on the current engine and identify its cause.

      3. 03

        Implement

        Add the change to its phase. Make optional behavior configurable per run.

      4. 04

        Test

        Run regression cases, workspace tests, and specification checks.

      5. 05

        Measure

        Compare output and speed before and after, and record the results.
